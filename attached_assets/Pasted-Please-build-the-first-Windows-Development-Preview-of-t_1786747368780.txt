Please build the first **Windows Development Preview** of the LSN Engineering Console from the existing web application and connect it to the new **Downloads** area.

The goal is to get the firmware engineer using the same Console locally as soon as possible so he can review the workflow, suggest changes, and begin real WT32-ETH01 integration while the web simulator and desktop application continue evolving in parallel.

This is an early engineering build, not a production release.

# 1. Preserve One Shared Codebase

The Windows application and web application must remain two deployment targets of the same LSN Engineering Console codebase.

Do NOT create or maintain a second independent Windows UI.

Reuse the existing:

* React components
* navigation
* styling
* guided tour
* password/auth experience where appropriate
* Simulation Mode
* Device Profiles
* firmware-facing interface specification
* Firmware Integration Package generator
* automated tests
* runtime/timer workflows
* Protocol Inspector
* stress testing
* firmware update simulation
* modules
* logs/reports
* Help / Firmware Guide
* Downloads content
* Firmware Developer Mode

Changes to shared UI, Device Profiles, simulator behavior, test definitions, expected behavior, documentation, and modules should benefit both web and desktop versions automatically.

Conceptually:

```text
Shared LSN Engineering Console
        |
        +-- Web build
        |     Simulation / documentation / downloads
        |
        +-- Windows Electron build
              Simulation
              +
              future real Hardware Mode
              local Ethernet access
              local firmware maintenance
```

# 2. Use Electron

Package the existing application as a native Windows desktop application using Electron.

Use:

* Electron
* existing React/TypeScript frontend
* Electron Forge for packaging

Do not switch this project to Tauri unless there is a critical technical blocker that must first be explained.

The architecture already assumes Node/Electron main-process networking for future EtherNet/IP and local firmware update transports.

# 3. Desktop Security Architecture

Use appropriate Electron security practices:

* `contextIsolation: true`
* `nodeIntegration: false` in the renderer
* narrow typed preload API
* local Ethernet/network operations belong in the Electron main process
* renderer communicates through typed IPC/preload interfaces
* no unnecessary direct filesystem or OS access from the renderer

Do not expose unrestricted Node APIs to the UI.

# 4. Keep Simulation Mode Fully Functional

The first Windows Development Preview must immediately support the same Simulation Mode already available in the web application.

The firmware engineer should be able to:

* launch the Windows app
* take/replay the guided tour
* discover `LSN-SIM-001`
* connect/disconnect
* use Control
* inspect Status
* run Runtime Observation
* run Timer Test
* run Persistence Test
* run Automated Validation
* run Stress Tests
* inspect protocol transactions
* review Device Profile
* enable Firmware Developer Mode
* generate the Firmware Integration Package
* simulate firmware updates and rollback
* export logs/reports/support bundles

Do not delay the desktop build until physical EtherNet/IP communication is complete.

# 5. Hardware Mode Architecture

Add/retain the desktop-only architecture required for future real WT32-ETH01 access.

Create typed replaceable adapters such as conceptually:

```text
ControlTransport
    |
    +-- SimulationTransport
    |
    +-- EtherNetIPHardwareTransport
```

and:

```text
FirmwareTransport
    |
    +-- SimulationFirmwareTransport
    |
    +-- LocalEthernetFirmwareTransport
```

The actual names may follow current code conventions.

For this Development Preview, Hardware Mode may remain incomplete where the real firmware and CIP mappings do not yet exist.

Clearly show appropriate states such as:

* AWAITING FIRMWARE IMPLEMENTATION
* PROTOCOL MAPPING TBD
* HARDWARE VALIDATION REQUIRED
* MAINTENANCE ENDPOINT NOT YET IMPLEMENTED

Do not fake communication with physical hardware.

# 6. Prepare Real Local Ethernet Access

The Windows app must be structurally capable of direct communication with devices on the local LAN.

The future real transport will communicate with the WT32-ETH01 through its built-in Ethernet connection.

Ensure the desktop architecture can support:

* UDP EtherNet/IP discovery / ListIdentity
* TCP EtherNet/IP session communication
* CIP explicit messaging
* future connected/implicit I/O
* device timeouts/reconnect
* raw TX/RX capture
* local firmware update transport
* rediscovery after device reboot

These do not all need to be fully operational in this preview if real firmware mappings/endpoints do not yet exist.
