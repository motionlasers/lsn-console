## 1. Correct Firmware Status vs Simulation Status

The Device Profile currently shows the status relationship backwards.

At this stage, the simulator has been implemented and validated, but the real WT32-ETH01 firmware has NOT yet been implemented or verified.

Therefore, for Phase 1 fields such as:

* `EmissionEnableRequest`
* `EmissionControlOutputActive`
* `Ready`
* `Faulted`
* `FaultCode`
* `TimerState`
* `LifetimeEmissionTimeMs`
* `EnableCount`
* `ProtocolVersion`
* other real-device protocol fields

the status should generally be:

**Firmware Status:**
`TBD`
or
`AWAITING FIRMWARE`

**Simulation Status:**
`VERIFIED`

where the simulator behavior has actually been tested successfully.

Do not use simulator success to mark the real ESP32 firmware as IMPLEMENTED or VERIFIED.

Keep the two status concepts separate everywhere they appear:

* Device Profile
* Firmware Developer Mode
* firmware-facing interface specification
* reports
* implementation checklists

Later, as the firmware engineer implements the real interface, Firmware Status can progress through:

* TBD
* IMPLEMENTING
* TESTING
* IMPLEMENTED
* VERIFIED

## 3. Implement the Actual Timer Test Workflow

The current runtime-filtered validation test is not a substitute for the guided Timer Test.

Create a dedicated Timer Test workflow.

It should:

1. Read the starting lifetime runtime.
2. Confirm the simulated device is connected.
3. Enable the emission-control output.
4. Start PC-side elapsed timing.
5. Maintain enable for a defined test duration.
6. Disable the output.
7. Read the ending runtime.
8. Calculate expected elapsed time.
9. Calculate LSN-reported runtime increase.
10. Calculate the difference.
11. Compare using a configurable tolerance.
12. Display PASS or FAIL.
13. Preserve all evidence in logs/reports.

Result view should show clearly:

* Starting Runtime
* Ending Runtime
* PC Measured Duration
* LSN Reported Increase
* Difference
* Allowed Tolerance
* PASS / FAIL

Simulation Mode must support this deterministically.

## 4. Implement the Actual Persistence Test Workflow

The current Persistence Recovery item is useful, but we also need the guided lifetime-counter persistence test.

Create:

**RUN PERSISTENCE TEST**

Workflow:

1. Read current lifetime runtime.
2. Record the before value.
3. In Hardware Mode, instruct the engineer to power-cycle the LSN and click Continue.
4. In Simulation Mode, simulate the equivalent device restart/power-cycle.
5. Rediscover/reconnect.
6. Read lifetime runtime again.
7. Compare before and after.
8. Verify the counter did not reset or decrease unexpectedly.
9. Display PASS / FAIL.
10. Allow engineering notes.
11. Preserve all evidence in session logs and reports.

Display:

* Before Power Cycle
* After Power Cycle
* Difference
* Firmware Version before/after if relevant
* Result
