# Build the LSN Engineering Console

Build a professional, local-first desktop engineering application named:

**LSN Engineering Console**

LSN stands for **Laser Safety Network**.

This application will become the permanent engineering, firmware-development, validation, diagnostic, commissioning, service, and reference-client platform for our LSN hardware.

The immediate Phase 1 goal is to help our embedded firmware engineer implement and validate EtherNet/IP communications, LSN control functions, lifetime runtime tracking, and firmware updates on the current WT32-ETH01-based LSN hardware with the least possible engineering overhead.

The firmware engineer should NOT need to create PC test software, temporary test scripts, packet decoders, GUIs, firmware-loading utilities, or repetitive validation procedures.

The console should make the development loop:

**compile firmware → install firmware over Ethernet → reconnect → run tests → inspect exact request/response → fix firmware → repeat**

as fast and transparent as possible.

This is NOT a one-off application for one client.

Build it as the permanent **LSN Engineering Platform** that can expand over time to support:

* sensors
* additional daughterboards
* monitored inputs
* remote-stop hardware
* relay outputs
* analog functions
* environmental monitoring
* multiple LSN devices
* commissioning
* diagnostics
* firmware management
* local firmware updates
* AWS field OTA
* additional protocols
* future safety-related architectures
* future LSN hardware generations

Initial release:

**LSN Engineering Console v0.1**

# 1. Confirmed Current LSN Hardware

The current LSN controller hardware consists of:

* Wireless-Tag **WT32-ETH01**
* ESP32 processor
* LAN8720A Ethernet PHY
* RMII Ethernet
* 10/100BASE-T Ethernet through the built-in RJ45
* existing custom LSN I/O daughterboard

All relevant WT32-ETH01 I/O is already routed through the existing daughterboard.

The WT32-ETH01 plus daughterboard combination has already operated successfully in field deployments for several years.

Therefore, for Phase 1:

* treat the existing daughterboard as established working hardware
* do not redesign it
* do not reverse-engineer it
* do not require GPIO-level configuration in the normal console workflow
* do not tie the external EtherNet/IP interface to physical GPIO numbers
* do not make the PC application dependent on the current daughterboard layout

The console communicates using **logical LSN functions and states**.

The ESP32 firmware is responsible for mapping those logical functions to the existing hardware.

Architecture:

PC Application
→ EtherNet/IP / CIP
→ LSN Logical Interface
→ LSN State Machine
→ Firmware Hardware Abstraction
→ Existing Daughterboard
→ Controlled Hardware

This abstraction is intentional.

Future daughterboards should be replaceable without requiring changes to:

* the external EtherNet/IP interface
* client integrations
* the core LSN Engineering Console
* the logical LSN state model

An optional developer-only Hardware Mapping area may exist later, but exact GPIO definitions are not required for Phase 1.

Use a desktop architecture suitable for direct local Ethernet access.

Preferred stack:

* Electron
* React
* TypeScript with strict mode
* Vite

* TCP session
* CIP explicit messaging
* error decoding
* timeouts
* reconnect
* raw packet logging
* connected messaging later
* I/O Assemblies later

## LSN Maintenance Transport

Separate from normal EtherNet/IP control traffic.

This transport handles:

* local firmware transfer
* firmware metadata
* firmware verification
* installation progress
* reboot
* firmware-update status

Do NOT require firmware images to be transported through EtherNet/IP/CIP unless there is a strong future engineering reason.

The same physical RJ45/Ethernet connection is used, but firmware maintenance should remain logically separate from industrial control communications.

## Device Profile Layer

Defines LSN protocol mappings and capabilities.

## Expected Behavior Engine

Defines what firmware and hardware should do.

## Test Engine

Runs automated and guided tests.

## Logging Layer

Records communications and engineering events.

## Report Layer

Exports evidence/results.

## Firmware Update Manager

Handles local firmware package validation, transfer, reboot, rediscovery, and post-update validation.

## Module Framework

Allows future LSN hardware/features to add states, commands, diagnostics, tests, and UI.

# 9. Requested vs Reported vs Hardware State

Always visibly distinguish:

## REQUESTED STATE

What the PC requested.

## LSN REPORTED STATE

What the firmware/state machine reports.

## HARDWARE CONTROL STATE

What LSN reports its physical control output is doing.

Example:

Requested:
`ENABLE`

LSN:
`READY / ENABLE PERMITTED`

Hardware Control:
`ACTIVE`

Timer:
`COUNTING`

Blocked example:

Requested:
`ENABLE`

LSN:
`BLOCKED`

Reason:
`REMOTE STOP OPEN`

Hardware Control:
`INACTIVE`

Timer:
`NOT COUNTING`

Never assume:

**Request sent = physical action occurred.**

# 25. Firmware Update Architecture

Design the LSN firmware around one common device-side firmware update subsystem:

```text
Local LSN Console ─────┐
                       │
                       ▼
              Firmware Update Manager
                       │
AWS OTA / IoT ─────────┘
                       │
                       ▼
               Validate firmware
                       │
               Verify compatibility
                       │
                Verify signature
                       │
              Write inactive OTA slot
                       │
                  Verify image
                       │
                    Reboot
                       │
                  Device self-test
                       │
            Accept firmware or rollback
```

The transport/source may differ.

But these should be shared:

* package validation
* target validation
* version validation
* cryptographic verification
* OTA partition handling
* reboot
* self-validation
* firmware acceptance
* rollback logic

Do not create completely unrelated local and AWS OTA implementations unless required by unavoidable platform constraints.

# 29. OTA Partition / Rollback Architecture

The current firmware engineer should design the ESP32 flash layout for OTA from the beginning.

The Console documentation should expect an OTA-capable partition structure with:

* bootloader
* partition table
* persistent configuration/NVS
* OTA metadata
* application slot A
* application slot B

Exact partition sizes are the firmware engineer's decision.

The Console must not hard-code partition offsets.

Support the concept of:

Current Firmware
→ Install to inactive slot
→ Reboot into new firmware
→ New firmware performs self-validation
→ Mark valid
OR
→ Roll back to previous firmware

# 32. Initial Programming and Recovery

Do not assume Ethernet can replace all physical programming forever.

Document that initial provisioning or recovery from severely damaged firmware may still require the WT32-ETH01 serial/programming interface.

However, the intended long-term normal workflow is:

**Ethernet firmware update through LSN Engineering Console**

Physical programming should become:

* first provisioning
* bootloader/partition provisioning if necessary
* emergency recovery

The console should not attempt to replace the ESP32 ROM recovery programmer.

**Emission Control Output Active**

rather than:

# 56. Important Firmware Boundary

The Console defines and tests the external logical interface.

It does NOT dictate how firmware maps those logical functions to the existing daughterboard.

Example:

Console:

`EmissionEnableRequest = true`

Firmware:

evaluates LSN state machine

Hardware abstraction:

drives existing daughterboard

Console:

reads `EmissionControlOutputActive`

Preserve this boundary.

# 58. Final Product Philosophy

The LSN Engineering Console should become the permanent engineering companion to the LSN platform.

Today it tests and manages:

* EtherNet/IP
* control requests
* reported states
* interlocks
* remote stop
* timer
* lifetime counter
* faults
* firmware installation
* firmware validation
* rollback

Later it should support:

* sensors
* additional daughterboards
* additional I/O
* multiple devices
* environmental monitoring
* commissioning
* diagnostics
* additional protocols
* AWS fleet OTA
* future LSN platform functions

Favor:

**stable logical interfaces + hardware abstraction + versioned Device Profiles + modular capabilities + shared firmware-update infrastructure**

rather than one-off customer-specific implementations.

When architectural choices conflict, prioritize:

1. firmware-engineer efficiency
2. reliable local firmware updating
3. transparent communications
4. clear expected behavior
5. modular expansion
6. hardware abstraction
7. deterministic testing
8. offline/local operation
9. maintainability
10. professional engineering UX

Do not sacrifice engineering transparency for visual simplicity.

Begin by building the complete v0.1 framework in Simulation Mode.

Implement Hardware Mode structurally.

Leave final CIP mappings as TBD until supplied by the firmware engineer.

Treat **local Ethernet firmware updating through the LSN Engineering Console as a permanent first-class LSN feature**, with the architecture prepared so future AWS field OTA can use the same underlying device-side validation, OTA partitioning, acceptance, and rollback mechanisms.
