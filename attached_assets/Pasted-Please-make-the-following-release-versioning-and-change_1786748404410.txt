Please make the following release/versioning and changelog update to the LSN Engineering Console before completing the Windows Development Preview.

This should establish a permanent release-history system for the Console while keeping the Console version, LSN Protocol version, Device Profile version, and firmware interface version clearly separate.

# 1. Update the Console to v0.2.0 Development Preview

The first Windows Development Preview provided to the firmware engineer should be:

**LSN Engineering Console v0.2.0 Development Preview**

This version applies to the Console software only.

Keep the current external firmware-interface versions unchanged:

**Console Version:**
`v0.2.0 Development Preview`

**LSN Protocol Version:**
`v0.1`

**LSN Device Profile Version:**
`v0.1`

**Firmware Integration Package:**
`LSN-Firmware-Interface-v0.1`

Do not change the LSN Protocol or Device Profile merely because the Console software version increases.

# 2. Keep the version tracks separate permanently

The application must clearly distinguish these version tracks.

## Console Version

Tracks changes to the web/Windows engineering software.

Examples:

* v0.2.0
* v0.2.1
* v0.3.0
* v1.0.0

## LSN Protocol Version

Tracks changes to the external client ↔ LSN communication contract.

Examples:

* v0.1
* v0.2
* v1.0

## Device Profile Version

Tracks the corresponding LSN Device Profile/interface definition.

## Firmware Integration Package Version

Tracks the firmware-interface/profile it represents.

For the current release:

```text
Console                  v0.2.0 Development Preview
LSN Protocol             v0.1
Device Profile           v0.1
Firmware Interface       v0.1
```

This distinction is intentional.

# 10. Add protocol-impact visibility to every future changelog entry

Every future Console release should explicitly say whether it affects the firmware protocol.

Examples:

### No protocol impact

`LSN Protocol remains v0.1. No firmware-interface changes are required.`

### Additive protocol update

`LSN Protocol updated from v0.1 to v0.2. Review the updated Firmware Integration Package.`

### Breaking protocol update

Clearly label:

**BREAKING PROTOCOL CHANGE**

and identify:

* old Protocol version
* new Protocol version
* affected fields/mappings
* firmware action required

This should help the firmware engineer immediately determine whether a new Console release requires firmware changes.

# 11. Add Device Profile impact to every future release

`Device Profile unchanged: v0.1`

`Device Profile updated to v0.2`

* fields removed
* types changed
* mappings changed
* capabilities added
* test expectations changed
