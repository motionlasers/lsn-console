# 1. Verify the Three Roles

Verify these exact roles:

* Superadmin
* Firmware Admin
* Client Reviewer

Create:

`01-role-permission-matrix.csv`

with columns:

* Capability
* Superadmin
* Firmware Admin
* Client Reviewer
* UI Enforced
* Server/API Enforced
* Test Result
* Notes

At minimum verify the following permissions.

## Superadmin

Must be able to:

* view all profiles
* edit profiles
* publish Development Profiles
* promote Production/Frozen Profiles
* manage users
* assign roles
* view audit history
* roll back Development Profiles

## Firmware Admin

Must be able to:

* view profiles
* edit Draft Profiles
* change CIP mappings
* change implementation status
* change update rate / RPI
* change timeout values
* run Simulation Mode
* generate Firmware Integration Packages
* submit for Client Review
* view Client Review comments
* publish an accepted Development Profile
* roll back a Development Profile
* view profile history/diffs

Must NOT be able to:

* manage users
* assign roles
* change global security settings
* promote Production/Frozen Profiles
* delete protected audit history

## Client Reviewer

Must be able to:

* view Review Candidate
* view object/tag map
* view connection model
* view RPI/update rate
* view communication-loss behavior
* view runtime behavior
* run Simulation Mode
* use Client Sandbox
* view diffs
* comment
* ACCEPT REVIEW
* REQUEST CHANGES
* download approved client-facing resources

Must NOT be able to:

* edit shared Device Profile
* change CIP mappings
* change implementation status
* publish
* roll back profiles
* promote production
* manage users
* change security settings

# 8. Critical Test: Verify Profile Changes Reach Windows Without Rebuilding the App

This is one of the most important verification items.

Demonstrate that a Device Profile/CIP mapping update does NOT require a new Windows application build.

Use the same Windows Console application version before and after the profile change.

Example:

```text
Windows Console:
v0.2.0 Development Preview

Installed Profile:
v0.1.3

New Published Development Profile:
v0.1.4
```

Verify the Windows Console:

1. Detects that a newer published Development Profile exists.
2. Displays:
   **NEW PROFILE AVAILABLE**
3. Shows the profile version.
4. Provides:
   **VIEW CHANGES**
5. Displays a mapping diff.
6. Provides:
   **APPLY PROFILE UPDATE**
7. Applies the updated profile.
8. Reports the new active Device Profile version.
9. Uses the new mapping in its runtime protocol configuration.
10. Does not require reinstalling or rebuilding the Windows application.

Capture:

`08-windows-profile-update-detected.png`

`09-windows-profile-diff.png`

`10-windows-profile-applied.png`

The key proof is:

**Device Profile changed, Windows application binary did not.**

# 10. Verify Updated CIP Mapping Is Actually Used by the Windows Console

After applying the new published profile, demonstrate that the Windows Console's protocol layer now resolves the canonical field using the updated mapping.

For the artificial TimerState test example, show conceptually:

```text
Canonical Field:
TimerState

Active Mapping:

Class:
0x70

Instance:
1

Attribute:
4
```

In Simulation Mode or a safe transport test, show that the Protocol Inspector reflects the currently loaded mapping.

Do NOT pretend this means the physical ESP32 firmware implements that mapping.

The evidence should prove only that the Windows Console dynamically consumed the published Device Profile.

# 11. Explicitly Confirm What Does NOT Propagate Automatically

In `00-VERIFICATION-SUMMARY.md`, include this statement clearly:

> Publishing a Device Profile changes the runtime configuration used by the web Console and Windows Console. It does not rewrite or automatically modify the ESP32 firmware. The firmware implementation must expose matching CIP objects/mappings before physical hardware testing can succeed.

This distinction is required.

# 12. Verify Profile Updates Do Not Trigger Windows Builds
